# Terminals

## Terminal Emulators

### Ghostty
- Config: `dot_config/ghostty/config.ghostty`
- Font: Fira Code Retina + FiraCode Nerd Font Mono, size 14
- Theme: Snazzy, background opacity 0.85 with macOS glass blur
- `auto-update-channel = tip` (follows tip/nightly)
- Quick terminal: `super+backtick`

### WezTerm
- Config: `dot_config/wezterm/wezterm.lua`
- Plugins: smart_workspace_switcher (zoxide-backed), sessionizer, resurrect (workspace save/restore), smart-splits (nvim integration), toggle_terminal
- Color scheme: Snazzy, font: Fira Code weight 450 with Nerd Font fallback
- WebGpu frontend, background opacity 0.90 with macOS blur
- `cmd+d` toggles vsplit with zoom behavior, `cmd+k` switches workspace via zoxide
- `cmd+shift+n` creates new named workspace
- `cmd+shift+p` opens command palette (with rename tab/workspace, save/restore workspace)
- smart-splits: `ctrl+hjkl` for movement (passes through to nvim), `meta+arrows` for resize
- `wezterm-switch-workspace` shell function uses user-var protocol to switch workspaces from CLI

### Kitty
- Config: `dot_config/kitty/kitty.conf`
- Font: Fira Code, Nerd Font via `symbol_map`, size 14
- Remote control enabled (`allow_remote_control yes`, `listen_on unix:/tmp/mykitty`)
- Layout: splits, theme: snazzy.conf (included)
- `macos_option_as_alt yes`
- Navigation integrated with nvim via `pass_keys.py` kitten (`ctrl+hjkl`)
- Session files live in `dot_config/kitty/sessions/`. `dashboard` is what `J launch-dashboard` opens: one OS window with a tab each for `gh dash`, `btm` and `mission-control --watch 2`. kitty draws its tabs inside one OS window, so AeroSpace sees a single window; a Ghostty tab is a separate macOS window, and a second tab in a scratchpad Ghostty window left it unusable (2026-10-08, cause not found)
- The remote-control socket is `/tmp/mykitty-<pid>`, not the bare `/tmp/mykitty` from `listen_on`

## zmx
- Session persistence (the keep-alive half of tmux); every wezterm window/tab/split auto-attaches to a fresh DBZ-named session via `zn` (wezterm `default_prog` → `zsh -c "zn; exec zsh -l"`)
- `dot_local/bin/executable_zn` — `export SHELL=/opt/homebrew/bin/zsh`, then `bmx new --detach --label owner=alex "$(dbzname)"` and `exec bmx attach` on that name. `bmx new` refuses a taken name with exit 5, and `zn` rolls a new name only then, up to `--tries` (default 3) times; any other failure exits 1. Since 2026-10-06 the session's host is `bmx` (`~/Code/lulu-tools`, in `~/.cargo/bin`), which speaks zmx's wire. Since 2026-10-08 everything here calls `bmx` as well: the `zmx-*` tools read `bmx list --json`, the precmd hook runs `bmx env -s .`, `zmx-agent-label` runs `bmx label .`, and `zn` creates with `bmx new` (2026-10-22). `bmx` is a client for zmx daemons too, so all of it works on a session either program hosts (run inside one of each on 2026-10-08). Nothing calls the `zmx` binary unless `bmx` is missing or `bmx version` fails: then `zn` hosts with zmx (its old loop: `zmx list --short`, then `zmx attach --labels`) and the precmd hook asks zmx. The fallbacks stay until bmx is published (bead `tools-8amh.64` in lulu-tools). `ZN_HOST=zmx` hosts with zmx on purpose. Typed inside a bmx session, `zn` moves that terminal to the new session (bmx never nests by default); inside a zmx session it opens the new one there, as before. The p10k segment `my_zmx_session` prints the name in magenta when `$BMX_SESSION` equals `$ZMX_SESSION`. `owner=alex` marks a session a person opened from a terminal, set at creation; agent-launched sessions (`bmx run`, the review launcher) don't pass through `zn`. `bmx list --where owner=alex` lists them, as does `zmx-ps --label owner=alex`. `bmx dash` is the session picker.
- **Session shells are homebrew zsh, deliberately.** Three-layer chain: wezterm copies `zmx_cmd`'s argv0 into every pane's `SHELL` env (appends duplicates; getenv takes the first), the session's host (a bmx host, or zmx's daemon) spawns the login `$SHELL`, and atuin's hex pty-proxy (`exec atuin pty-proxy` in zshrc) respawns `$SHELL` via portable_pty. Bare `"zsh"` resolves through the minimal launchd PATH to Apple `/bin/zsh`, whose exec-time env is hidden from `ps eww` (KERN_PROCARGS2 — Apple platform binaries only); homebrew zsh exposes it. Hence full paths in wezterm.lua's `zmx_cmd` AND the `SHELL` export in `zn`.
- **Two distinct state axes — don't conflate them:** *session occupancy* (`active`/`idle` — the process tree holds a real workload vs only shells/atuin-proxy) is NOT a Claude agent's own *turn-status* (`busy`/`waiting`/`idle` from `claude agents --json`). A session can be `active` with no agent in it; an `idle` agent can sit in an `active` session. zmx-ps/zmx-reap report occupancy; agent-sessions shows both side by side.
- **Nim core in `scripts/zmx/`** (the migration off Bash/awk/jaq is complete: all seven tools are Nim; only the launchers `zn` and `dbzname` stay Bash). Sibling modules, imported by bare name: `zmx_types` (domain types with `distinct` `ZmxSessionName`/`ProcessId`/`ClaudeSessionId`/`CodexSessionId`, the enums `AssociationSource`/`AgentProvider`/`AgentKind`/`AgentStatus`/`ReapVerdict`, the wire types `SessionOut`/`ProcOut`/`WhichOut`/`AgentOut`, the `ZmxJson` flavor that writes absent optionals as `null`, and `ClaudeJson` for decoding other tools' output), `zmx_sessions` (`bmx list --json` into `ZmxSession` through `parseList`, with `epochOf` turning its RFC 3339 `created_at` into epoch seconds; `Result`-returning `listSessions`; `pinEnvironment` for `PATH`, which now holds `~/.cargo/bin`, and `TMPDIR`), `proc_table` (process readers, tree walk, occupancy, `readEnvVar` for one variable and `readEnv` for a whole environment), `zmx_snapshot` (`snapshot()`: every session with its tree and occupancy, and `reapVerdict`), `zmx_agents` (`claude agents --json` into `AgentSession`, `associate`, and `resolveAgents()`: sessions, agents and their associations in one value, the read `zmx-which`, `agent-sessions` and `mission-control` all start from), `git_head` (`branchOf`: the branch from `.git/HEAD`, following a worktree's `gitdir:` file, no `git` spawn), `codex_sessions` (`recentCodexSessions`: rollouts by mtime, line one decoded), `agent_rows` (the `AgentOut` rows, status cells, `watchArgs` and the `hark` handoff), `term_out` (colours, glyphs, `layout` and `clip`; the zmx tools draw everything in-process and none of them starts `gum`), the cligen binaries `zmx_ps`, `zmx_which`, `agent_sessions`, `mission_control`, `zmx_reap` and `zmx_env`, and `zmx_agent_label`, which parses its two arguments by hand. `zmx-select` and its `zmx_picker` module were deleted on 2026-10-22 for `bmx dash`; the rest go once bmx reports what they read (beads `tools-8amh.59`-`.63` in lulu-tools: per-process start time and memory, exec-time environments, the occupancy rule below). `run_onchange_build-scripts.sh.tmpl` builds the seven from its `builds` list and hashes every module under `scripts/zmx/` once; a new module needs a hash line there. Libraries: `cligen`, `json_serialization`, `results`, `regex`, and `unittest2` for `test_zmx_core.nim`.
  - **Claude's `kind`, `status` and `state` stay strings.** Claude owns those sets, and a closed enum on the decode type would fail the whole listing on a value it adds. `kindOf` and `turnStatusOf` classify them into `AgentKind` and `AgentStatus` (each with an `Other` member) for sorting and colour, and `--json` echoes the raw string. `Option` fields decode absent and `null` alike to `none`.
  - **`--watch [SECS]` runs through `hark`.** `watchArgs` rewrites a bare `--watch` to `--watch=2` and `--watch 5` to `--watch=5` before cligen parses, which is why those two binaries use `dispatchCf` (only it takes `cmdLine`). The binary then `execv`s `hark run -e <n>s -- <itself> --within <min>`, looking in `~/.cargo/bin` when `hark` is off the pinned `PATH`, and exits 1 when there is none. `hark` prints its own `Every 2s: ...` header above each frame.
  - **`layout` sizes columns to content.** Cells carry their own SGR colour; `visibleLen` counts runes outside escapes, every column but the last pads to its widest cell, and a column empty in every row is dropped. Glyphs are `\uXXXX` constants in `term_out`.
  - **Process reading is native.** `proc_table` asks libproc: `PROC_PIDT_SHORTBSDINFO` for every pid's parent (it answers for root-owned processes; `PROC_PIDTBSDINFO` does not), then start time, memory and `KERN_PROCARGS2` argv only for session descendants. `ZMX_PS_SOURCE=ps` forces the `ps -axo` reader, which is also the fallback and what the stubbed tests use. 27 ms against the Bash version's 185 ms, most of which was `ps` formatting 2,600 processes.
  - **cligen gotchas:** `clCfg.longPfxOk = false` is required. With prefix matching on, `--name RE` is read as the boolean `--names`. `cgParseErrorExitCode = 2` makes an unknown flag exit 2; the default is 1. A flag hidden from `--help` takes the literal `"CLIGEN-NOHELP"` in the `help` table (the table is read in a macro, so `clCfg.hTabSuppress` does not compile there), and a hidden boolean drops off cligen's list of valueless flags: `--emit --here` reads `--here` as `--emit`'s value, so a hidden flag goes last. `suppress` is not the tool for hiding: it stops the flag being parsed at all.
- Inspection/cleanup tools, all Nim binaries built from `scripts/zmx/`:
  - `zmx-ps` — Nim binary. Every session as JSON (info + `labels: {k: v}` + descendant `procs: [{pid, etime, rss_kb, command}]` + `state: active|idle` occupancy verdict + `running: <program>`); filter flags `--name/--dir/--hosting RE`, `--label K[=V]`, `--detached/--attached`, `--active/--idle`, `--names` for xargs. It is `bmx list --json` plus what runs in each session. `etime` and `rss_kb` are `null` when the kernel withholds them (a root-owned child). Siblings under one parent come in ascending pid order, which is not `ps`'s order. Labels are the row's `labels` object; a daemon's `cmd` and `task` are fields of their own. `current` is true for the session `$ZMX_SESSION` names. A row with no pid, or with a `created_at` that cannot be read, is skipped.
  - `zmx-agent-label set|unset <agent>` — run by Claude's `SessionStart` / `SessionEnd` hooks (`claude-settings.json`) with the hook JSON on stdin. Labels the ambient `$ZMX_SESSION` with `agent=claude claude_session=<session_id> claude_pid=<CLAUDE_PID>`. Identity only: turn state never goes in labels. `set` refuses when another live pid owns the labels (a nested `claude -p` inherits `ZMX_SESSION`). On a bmx host `set` passes `--owner-pid <CLAUDE_PID>`, so the host drops the three labels when that process goes, however it ends; a zmx daemon answers exit 2 for an owner, and the hook then sets them without one. `unset` removes those three keys only, and only while `claude_session` still names the ending session, so `/clear`'s `SessionEnd` can't erase the id the following `SessionStart` wrote. It reads with `bmx label . --json` and writes with `bmx label . k=v` (`k=` removes a key), and never passes `--clear`; foreign labels (the cleverific reviewer launcher's `role=`/`session=`) survive. Exits 0 on everything but a usage error (2), so a hook can't block the agent: empty or non-JSON stdin, a `session_id` outside `[A-Za-z0-9._-]`, and a failing `bmx` each end in a line on stderr. It prints nothing on stdout, the labels `bmx label` prints included, because a `SessionStart` hook's stdout lands in the agent's context.
  - `zmx-reap [--kill|-k] [--all|-a]` — kill detached sessions whose tree is idle; dry run by default, active sessions always skipped. `reapVerdict` over `snapshot()`: a client attached is `attached`, a detached session with work is `active:<program>`, the rest are `reap`. The `NAME AGE VERDICT DIR` table is drawn with `layout` in the Bash version's colours (red `reap`, yellow `active`, dim `attached` and directories), then a blank line and the summary, all on stdout. No `gum`: each `gum` start costs about 60 ms, as much as the session read itself, and `gum table --print` drops cell colours. `--all` also lists attached sessions, which makes it a full inventory. `--kill` runs one `bmx kill <names...>`. A failed session read or a failed `bmx kill` exits 1; the Bash version reported a failed read as "nothing to reap". About 67 ms against 144 ms, which is the cost of `snapshot()` over 63 sessions.
  - `zmx-which [--json] [session|pid]` — Nim binary; the agent ↔ zmx association as a command. `agent-sessions` and `mission-control` get the same answer in-process from `resolveAgents()`. Per agent, first hit wins: `label` (session's `claude_session` label equals the agent's `sessionId`), `process_env` (`ZMX_SESSION` in the exec-time env), `process_tree` (pid is a descendant of the session daemon). `--json`: `{pid, kind, status, session_id, cwd, zmx_session, association_source, clients, occ, turn_status, task_state, name, short_id, started}`. `status` is the same merge `agent-sessions` reports (`effectiveStatus`), so the two tools agree for every pid; `turn_status` and `task_state` are Claude's `status` and `state` as sent. A crashed agent's leftover label matches no live `sessionId`, so it's ignored. It reads sessions in-process through `snapshot()` (no `zmx-ps` subprocess) and takes `ZMX_SESSION` from the env strings that follow argv in `KERN_PROCARGS2`; `ZMX_PS_SOURCE=ps` switches that to `ps eww -p`. If `bmx list --json` or `claude agents` fails it prints the reason on stderr, lists nothing, and exits 0. The human table is drawn with `layout`: bold header, red `waiting`, yellow `busy`, everything else dim, a dim `-` for an absent value, and the agent's name in a `NAME` column before the directory. About 240 ms against the Bash version's 395 ms; `claude agents --json` alone is 180 ms.
  - `zmx-env <session> [pattern]...` — the exec-time environment of each process in a session, one `== <session> <pid> (<argv[0]>)` block per process, entries sorted by byte. Patterns are case-insensitive regexes (the `regex` package, no `rg` spawn), OR'd; a bad one exits 2, an unknown session 1, no session 2. The environment is read from `KERN_PROCARGS2`, so a value containing spaces stays whole; `ZMX_PS_SOURCE=ps` switches to `ps eww`, which joins the environment with spaces and makes `parsePsEnv` guess where a value ends. Apple platform binaries show no environment either way. It prints whole environments: pass a pattern when the output will be logged or shared. About 70 ms against 369 ms.
  - `agent-sessions [--within MIN] [--watch [SECS]] [--json]` — Nim binary; the agent-centric glance. `claude agents --json` is heterogeneous by kind: `interactive` (terminal sessions: `status` + pid → zmx session + occupancy) and `background` (headless tasks: `sessionId` + name + `state`, usually no pid). Interactive and Codex rows render as resumable sessions up top, waiting, then busy, then idle, newest first (each with its zmx session and occupancy or, for Codex, the first 8 characters of its `payload.id`); background agents get a dim section by name, short id and state. `--json` is the canonical per-agent array, Claude's agents in Claude's order, then Codex sessions newest first: `{source,kind,status,pid,session_id,short_id,name,cwd,branch,zmx_session,association_source,occ,idle_s,started,turn_status,task_state}`. `status` is the turn status for `interactive` (default `idle`) and the task `state` otherwise (default `?`); `turn_status` and `task_state` are Claude's `status` and `state` as sent, `null` when it sent none, because a background agent can carry both (`idle` and `done`). In the view a session row shows the agent's name after its branch, clipped to 28 characters with `…`, and how long ago a Claude agent started after its occupancy. Every agent that has a pid carries its zmx session, background ones included. `--within` bounds the Codex scan by rollout mtime (default 90; `0` matches nothing). `--json` wins over `--watch`; an unknown flag exits 2. A branch is `none` for a detached `HEAD` or an agent with no directory. About 230 ms against the Bash version's 605 ms.
  - `mission-control [--within MIN] [--watch [SECS]]` — Nim binary; the everything-alive superset, and what the zellij dashboard runs. Rows by priority, then newest, then directory: `cc` agents that have a pid (waiting 0, busy 1, the rest 3; status is Claude's `status`, never `state`), `cx` Codex sessions (2), and every zmx session hosting no listed agent (`shell` 4 when a client is attached, `detached` 5). A `cc` row shows the agent's name after its branch (clipped to 28 characters). The column after the status is the hosting zmx session; a trailing `·name` is the WezTerm workspace open on that directory, from `wezterm cli list --format json`. That call starts before the agent read and gets 400 ms from its start, because it hangs for about 2.3 s when WezTerm is closed; a miss is no tags. 415 ms with WezTerm closed (the deadline is the floor then), against the Bash version's 3.2 s; not yet timed with WezTerm answering, and its JSON shape (`cwd`, `workspace`) is taken from the Bash version, covered only by the harness stub.
- **Tracked env (zmx 0.8+).** `ZMX_TRACK_ENV` in `dot_zshenv` lists what zmx records from the attaching terminal: zmx's nine defaults restated (the variable replaces the built-in list), plus `TERM_PROGRAM`, `__CFBundleIdentifier`, `WEZTERM_PANE`, `WEZTERM_UNIX_SOCKET`, `BTTY_PANE`, `BTTY_TAB`, `BTTY_WORKSPACE`, `BTTY_SOCK`, `BTTY_DIR`. The `zmx attach` client reads it, not the daemon (`src/main.zig`, attach path), so it must be in the env of whatever runs `attach`, and a session only gains the new set at its next attach. `dot_zsh/zmx.zsh` registers `_zmx_refresh_env` with `add-zsh-hook precmd`: it evals `bmx env -s .` and returns the previous `$?` so p10k's status segment still sees it. `bmx env -s` prints byte for byte what `zmx print-env -s` does, and takes 4.0 ms where zmx takes 1.9 (hyperfine, 2026-10-08). With no `bmx` on PATH the hook runs `zmx print-env -s .`. Values come from the session's leader client; a second client that attaches doesn't replace them until it leads. **Boundary:** the hook updates the shell and what it starts next. A process already running keeps its exec-time env and has to query live: `bmx env . WEZTERM_PANE`. lulu-loadout's `lib/term_env.nim` does that for the notify hook, the statusline and `wezrun`. A terminal app launched from another terminal's shell inherits that terminal's pane id (WezTerm opened from btty tracks a live `BTTY_PANE`), so readers pick the terminal by tracked `TERM_PROGRAM`, which each terminal sets for its own panes. Fish has no hook yet.
- **Claude's session registry (not read yet; revisit).** The zmx tools take agents from `claude agents --json` only. Claude Code also keeps one file per session, `~/.claude/sessions/<pid>.json`, rewritten as the session changes. It is undocumented: the format comes from [PeterSR/claude-code-socket-transport](https://github.com/PeterSR/claude-code-socket-transport), a Go client whose `ListSessions` reads these files, and was checked here on Claude Code 2.1.286.
  - **Agrees with the CLI** on `pid`, `name`, `cwd`, `sessionId` and `startedAt` for every agent that has a pid.
  - **Adds** `statusUpdatedAt` (when the status last changed), `waitingFor` (what a waiting agent waits on), `version`, `nameSource`, `messagingSocketPath`, and a raw status `shell` that the CLI reports as `busy`.
  - **Lacks** the background tasks that have no pid, and a task's `state`. It spells the kind `bg`.
  - **Can be stale**: a file can outlive its process (one of 24 did), so a reader has to check the pid, or compare `procStart`.
  - **Never read the `.key` files beside it** (`<pid>.<hash>.key`): each holds that session's messaging token.
  - **What a later slice would gain**: `waiting_for` and `status_since` in the views, and listing without the 147 ms `claude agents` call. The cost is leaning on a format Claude Code can change in any release.
  - **The inbox socket is a separate thing**, and that one is documented ([cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging#the-sessions-inbox-socket)): each session binds `/tmp/cc-socks/<pid>.sock` and exports the path as `CLAUDE_CODE_MESSAGING_SOCKET`, so a script or hook can post a message into it. It is send-only. Nothing can be listed or read back through it but delivery receipts.
- Tests: `just test-zmx` runs the Nim unit suite (`scripts/zmx/test_zmx_core.nim`), then `scripts/zmx/test-zmx-tools.sh`, which builds all seven tools and runs them under a throwaway `HOME` with stub `bmx`/`claude`/`ps`/`wezterm` and one Codex rollout fixture. The stub `bmx` serves `list --json` from one JSON row a line, keeps `label` in a file (an `--owner-pid` goes to `$FIX/owner`, and a `no-owner` fixture file makes it exit 2 as a zmx daemon does), and exits 2 for any call it does not know; a stub `zmx` beside it exits 97, so a tool that fell back to zmx would fail a check. The stub `bmx kill` only records the names it was given; `zmx-reap --kill` was also run once against real sessions in a scratch socket directory (2026-10-08). The tools pin `$HOME/.local/bin` first on `PATH`, which is what lets the throwaway `HOME` put the stubs in front.
- Known edge: the list's pid IS the session's root process; the tools only inspect *descendants*, so a session created as `zmx attach name <cmd>` (root = workload, no children) reads as idle
- **Footgun:** `zmx attach <other>` from INSIDE a session doesn't nest — it switches the current client (the user's pane!) whenever `ZMX_SESSION` is set. `bmx attach` moves a terminal only when it runs on the session's own terminal (the one `BMX_TTY` names) and refuses otherwise unless `--nest`. Test session spawning with a scratch `BMX_DIR` in `tui-test`, or with `wezterm cli spawn`
